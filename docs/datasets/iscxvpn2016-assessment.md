# ISCXVPN2016 dataset assessment

**Status:** candidate only; not yet acquired or validated  
**Assessed:** 2026-11-03

## Why this dataset is relevant

The University of New Brunswick (UNB) Canadian Institute for Cybersecurity documents the VPN-nonVPN dataset (ISCXVPN2016) as real traffic captures generated by lab members. Its streaming category includes YouTube (HTML5 and Flash) and Vimeo captured using Chrome and Firefox. The dataset contains regular and VPN sessions across 14 traffic categories.

The official release includes packet-level PCAP files and derived flow CSV files generated by ISCXFlowMeter. The original paper describes the capture process and time-related flow features used in its classification experiments.

## Important limitations

1. **Not a clean YouTube-only trace by default.** The dataset contains multiple applications and traffic classes. The official description says unnecessary applications were closed during capture and packets were filtered by local client IP, but this does not prove every packet in a selected capture belongs to the target media session.
2. **File-level mapping is undocumented.** UNB's FAQ explicitly says it does not provide file-level mapping between PCAP and flow CSV files. Exact YouTube/Vimeo capture files must be established from the downloaded archive, accompanying metadata, and, if necessary, maintainer clarification.
3. **Flow CSV is not the primary source for packet time series.** The flow CSVs are derived by ISCXFlowMeter and contain selected flow-level features. Use PCAP for packet-level aggregation and treat CSV only as a cross-check after mapping is understood.
4. **Packet length needs precise naming.** PCAP captured length is not necessarily application payload length or even original wire length when packets are truncated or link-layer framing differs. The first derived metric should be named `captured_packet_bytes` unless validation justifies a different quantity.
5. **Not representative of all modern Internet traffic.** This is a 2016 laboratory capture of selected services and environments. It is a reproducible trace source, not a universal workload.

## Proposed first extraction protocol

After official acquisition and inspection:

- Start with non-VPN YouTube streaming captures if exact files can be identified confidently.
- Retain packet timestamps at their native precision until aggregation.
- Define a fixed bin width explicitly (initial comparison: 1 second, plus finer intervals if timestamps support it).
- Aggregate captured packet lengths by timestamp bin; document whether both directions and all local-client packets are included.
- Use a relative time origin at the first included packet and define bins as half-open intervals `[kΔ, (k+1)Δ)`.
- Preserve empty bins as zero; do not silently pad the observation to a power of two as part of capture preprocessing.
- Record exact archive/file checksums, source citation, retrieval date, tool versions, selected files, filters, and configuration in a machine-readable manifest.
- Keep raw PCAPs outside Git. Only commit code, metadata, and a small derived fixture if source terms and privacy review permit it.
